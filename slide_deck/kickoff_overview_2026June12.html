Agentic workflow

Chat answers.
An agent acts.

Claude Code can inspect files, run tools, observe the output, and repeat when the task requires it. You can interrupt or redirect the session at any point.

The agent loop

Most tasks follow the same
working loop.

01 Gather
context
→
02 Take
action
→
03 Verify
results

Repeat · course-correct · the researcher stays in the loop

Notes

You are inside this loop, not watching it. Interrupt at any point and redirect — you do not have to let a run finish to correct it. A question may need only the first phase; a bug fix can cycle through all three dozens of times.

Working context

The working context can include
code, tools, and documents.

The working set Files and tools available to the session
Repository filescode · tests · configuration
Terminal commandsbuild · run · inspect
Documentspapers · notes · specifications
Local toolsnotebooks · Wolfram · JAX
Connected servicesthrough authorized tools
Its own outputevidence for the next iteration

Notes

What is not in the working set matters as much as what is: anything outside the directory you started in, anything you have not shown it, and anything it cannot reach with a tool. It does not know your unpushed branches, yesterday's notebook output, or what you meant but did not write.

Boundaries

Permission rules decide
what it may touch.

01 · AUTOMATIC

Allow

Auto-approved — e.g. Read(**), Bash(pytest *).

02 · CHECKPOINT

Ask

Pauses for confirmation — e.g. Edit(**), Bash(git commit *).

03 · BOUNDARY

Deny

Always blocked — e.g. Read(./.env), Bash(rm -rf *).

Persistent context

Guidance gets more specific
as the work gets closer.

~/.claude/CLAUDE.md Personal defaults every repository
./CLAUDE.md Project conventions shared in the repo
./CLAUDE.local.md Local rules not shared, this project

Instruction files concatenate from the project root down toward where you are working — the closest guidance is read last.

Notes

If your repository already has an AGENTS.md for another agent, Claude Code does not read it directly — add a CLAUDE.md containing @AGENTS.md, or symlink one to the other, so both tools read the same instructions.

What goes wrong

Three failure modes worth
recognizing early.

01 · PLAUSIBLE

Confident and wrong

Fluent output is not evidence. An unverified result is a hypothesis.

02 · DRIFT

Silent scope creep

A small request grows extra edits. Read the diff, not the summary.

03 · REACH

Edits you did not sanction

Boundaries are configuration, not good intentions. Set them first.

Notes

A fourth mode: work better done by hand. If you can write it faster than you can specify it, write it. The loop pays off when verification is cheaper than production.

Instruction files are context, not enforcement — the agent reads them and tries to comply, but nothing guarantees it. For a hard guarantee, use a hook or a deny rule — a PreToolUse hook that exits 2 stops the call before permission rules are evaluated.

Session hygiene

A session has a working
memory, and it fills up.

01Scope the working set — point at the files that matter, not the whole tree
02Start fresh when the task changes — a long session carries its whole history
03Prefer one verified step to five unverified ones

Notes

Everything the session has read stays in context and is re-sent with each turn, so a long session is both slower and more expensive than a short one. Quality degrades too: relevant detail competes with everything read earlier.

Practical rule — one task per session. When you find yourself re-explaining what the session already did, start a new one and give it the conclusion rather than the history.

A reusable prompt recipe

A practical prompt
names its own finish line.

01ObjectiveWhat outcome matters?
02ContextWhich files, paper, or data should it use?
03ConstraintsWhat must remain unchanged?
04DeliverableWhich artifact should exist?
05VerificationWhat observation proves it works?

Notes

Before: "fix the covariance code." After: "The ℓ=4 entry disagrees with Eq. B2. Find the discrepancy, do not modify the notebook, and show me the two expressions side by side." The second names a symptom, a constraint, and the observation that ends the task.

Where to start

Five things, in this order.

01Write it downOne project instruction file. Conventions, build command, what not to touch.
02Set the boundaryDecide what runs without asking, and what always stops for you.
03Run something read-onlyOnboard it to a repository you already know. Check its answer.
04Add a finish linePut a verification criterion in one real prompt this week.
05Package what workedWhen you repeat a prompt a third time, make it a skill.

Notes

Three rungs, and most people should stay on the first two for a while: personal and project instruction files plus permissions; then installing and writing skills; then hooks, subagents, and MCP once a routine is stable enough to be worth automating.
